## What I do

Filter all conversation content in real-time and classify it into:
- **LOG**: Important project-related information
- **SUMMARY**: Brief context worth noting
- **DISCARD**: Casual conversation, jokes, emotions

## Storage Location

**All logged conversations go to:**
```
C:\Users\admin\Desktop\Fork\EndOfTale\.opencode\memory\daily\YYYY-MM-DD.md
```

- One file per day
- Auto-created if doesn't exist
- Appended throughout the day
- Cleared at midnight (new day = new file)

## Classification Rules

### 🔴 LOG (Project Critical)
**Log to daily memory file with full details**

Save detailed records of:
- Feature requirements or specifications
- Technical decisions and rationale
- Bug reports and reproduction steps
- Architecture changes
- Timeline or milestone discussions
- External dependencies or integrations
- Performance requirements
- Security considerations

**Format:**
```markdown
---
**YYYY-MM-DD HH:MM:SS**

## [LOG] Topic Title

**Decision/Requirement:** [What was decided or required]
**Context:** [Why this matters]
**Next Steps:** [What to do next]
**Related:** [Files, systems, people]
```

**Examples:**
- "We need to implement a save system using JSON"
- "The boss AI should have 3 phases at 70% and 30% health"
- "Player movement feels sluggish, let's increase speed to 8f"
- "Decision: Not implementing multiplayer for v1.0"

### 🟡 SUMMARY (Context Worth Noting)
**Log to daily memory file (brief entry)**

Save brief notes of:
- User preferences or habits
- Development environment details
- Third-party tool mentions
- Resource references
- Testing strategies
- Session start/end context

**Format:**
```markdown
---
**YYYY-MM-DD HH:MM:SS**

## [SUMMARY] Topic Title
[Brief 1-2 sentence summary]
```

**Examples:**
- User prefers dark theme
- Using Unity 6000.3.2f1
- References to external tutorials
- "I'll test this later" (note to remind)

### 🟢 DISCARD (Don't Log)
**Ignore completely - no record needed**

Do NOT save:
- Casual greetings and goodbyes
- Weather, food, personal life
- Jokes and teasing (even if project-related)
- Emotional reactions
- Off-topic discussions
- Repeated confirmations

**Examples:**
- "Hello!" / "Goodbye!"
- "It's raining today"
- "I'm hungry"
- "Haha that's funny"
- "Wait, really?"
- "Nice!" / "Cool!"

## Filtering Process

### Step 1: Real-time Classification
During conversation, continuously evaluate each statement:
```
User: "We should add a double jump mechanic"
→ Classification: 🔴 LOG (Feature requirement)
→ Action: Record in PROJECT_STATUS.md

User: "Haha, that bug is hilarious"
→ Classification: 🟢 DISCARD (Emotional reaction)
→ Action: Ignore

User: "I prefer using GitHub for version control"
→ Classification: 🟡 SUMMARY (Preference)
→ Action: Mental note, no file record
```

### Step 2: Decision Confidence

**High Confidence (>90%):**
- Clear technical instructions → LOG
- Clear casual chat → DISCARD

**Medium Confidence (70-90%):**
- Ask clarifying question silently
- Make best guess
- Err on side of logging if unsure

**Low Confidence (<70%):**
- Briefly consider context
- When in doubt: 🟡 SUMMARY (minimal record)

### Step 3: Context Awareness

**Consider conversation flow:**
- Previous 3-5 exchanges provide context
- Don't log repetitive confirmations
- Do log new information even if brief

**Example:**
```
User: "Add a health bar"
Me: "OK! Where should I put it?"
User: "Top left corner"
→ LOG: "Health bar UI - position: top left"

User: "No wait, bottom left"
→ UPDATE existing log, don't create new entry
```

## Special Cases

### Mixed Content
If a message contains both important and casual content:
- Extract and log the important part
- Discard the casual part
- Example: "Haha, good point! We should use singleton pattern here"
  - Log: "Decision: Use singleton pattern"
  - Discard: "Haha, good point!"

### Implicit Requirements
User might not explicitly state requirements:
- "This is too slow" → LOG: "Performance concern identified"
- "I don't like this color" → LOG: "UI color needs adjustment"

### Repeated Information
Don't duplicate logs:
- Check today's daily file first (`daily/YYYY-MM-DD.md`)
- Update existing entries instead
- Note: "Reaffirmed" or "Confirmed" if needed
- If same topic as previous day, link to previous entry

## Error Prevention

### Over-Logging Prevention
- If unsure, use SUMMARY instead of LOG
- Review daily file size - if too large, summarize older entries
- Archive daily files older than 30 days to `daily/archive/`
- MEMORY.md maintains index of archived conversations

### Under-Logging Prevention
- When user makes a decision → Always LOG
- When user mentions a constraint → Always LOG
- When user references external resource → SUMMARY minimum

## Important Principle

**Better to log too little than too much.**
- User can always provide missing context
- But bloated logs make finding information impossible
- Focus on decisions, requirements, and changes

## Integration with Other Skills

### With project-logging:
- **conversation-filter**: Saves conversations to `daily/` (대화 기록)
- **project-logging**: Saves project status to `PROJECT_STATUS.md` (프로젝트 상태)
- **Separation of concerns:**
  - Daily logs = Conversation history, decisions made during chat
  - PROJECT_STATUS.md = Current project state, TODOs, progress

### With session-handover:
- **conversation-filter**: Records detailed daily logs
- **session-handover**: Creates session summaries from daily logs
- **Workflow:**
  1. Daily conversations → `daily/YYYY-MM-DD.md`
  2. Session end → session-handover summarizes from daily log
  3. Next session → Read handover + recent daily logs
