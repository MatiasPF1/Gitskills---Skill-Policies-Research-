# Skill: Brainstorming

> Adapted from [obra/superpowers](https://github.com/obra/superpowers) (MIT) `skills/brainstorming/SKILL.md`.
> Superpowers is (c) Jesse Vincent / Prime Radiant.

## When to Load
- Before any creative work: new feature, new component, new behavior, or
  modification of existing behavior.
- At the very start of a feature request, BEFORE the planner agent runs.
- Whenever a request is ambiguous, under-specified, or hides assumptions.
- Do NOT load for: pure bug fixes (use `systematic-debugging`), pure refactor
  (use the refactor workflow), or single-line config changes.

## Core Idea

Turn a vague request into a vetted, written design before any plan is drafted
or code is written. Plans written against a vetted design reject far less
often. The interaction is Socratic: one question at a time, mostly
multiple-choice, with the design presented in digestible sections.

## Hard Gate

Do NOT invoke the planner, write code, scaffold files, or take any
implementation action until you have presented a design and the user has
approved it. This applies to EVERY request regardless of perceived
simplicity.

## Anti-Pattern: "This Is Too Simple To Need A Design"

Every change goes through this process. A todo list, a single utility, a
config change — all of them. "Simple" changes are where unexamined
assumptions cause the most wasted work. The design can be short (a few
sentences for truly simple changes), but you MUST present it and get
approval.

## Process

1. **Explore project context** — read `project/` files, recent commits,
   existing conventions. Do not propose anything without first
   understanding the surrounding code.
2. **Assess scope** — if the request describes multiple independent
   subsystems, flag it and help decompose into sub-projects. Each
   sub-project gets its own design -> plan -> implement cycle. Brainstorm
   the first sub-project only.
3. **Ask clarifying questions, one at a time** — purpose, constraints,
   success criteria. Prefer multiple choice. Never bundle multiple
   questions in one message.
4. **Propose 2-3 approaches with trade-offs** — lead with your
   recommendation and why. Do not present a single option as the only way.
5. **Present the design in sections** — scaled to their complexity (a few
   sentences if straightforward; up to 200-300 words if nuanced). Cover:
   architecture, components, data flow, error handling, testing. After
   each section, ask whether it looks right so far.
6. **Write the design doc** — save to
   `contexts/{feature-name}/00-spec.md` and ask the user to review it.
7. **Spec self-review** — scan the written spec for:
   - Placeholders (TBD, TODO, vague requirements)
   - Internal contradictions
   - Scope creep (needs decomposition into sub-projects)
   - Ambiguity (any requirement that could be read two ways)
   Fix issues inline, then ask the user to review the file.
8. **Transition** — once the user approves the spec, hand off to the
   `planner` agent (`/plan` or `agents/planner.md`) to produce
   `01-plan.md`. Do NOT invoke the implementer directly.

## Design for Isolation and Clarity

- Break the system into units that each have one clear purpose, communicate
  through well-defined interfaces, and can be understood and tested
  independently.
- For each unit, you should be able to answer: what does it do, how do you
  use it, and what does it depend on?
- If someone cannot understand a unit without reading its internals, the
  boundaries need work.
- Smaller, well-bounded units are easier for agents to reason about and
  edit reliably. A file growing large is often a signal it's doing too
  much.

## Working in Existing Codebases

- Explore the current structure before proposing changes. Follow existing
  patterns (see `rules/01-django-core.md`, `rules/02-drf-standards.md`).
- Where existing code has problems affecting the work (a file that's grown
  too large, unclear boundaries, tangled responsibilities), include
  targeted improvements as part of the design — the way a good developer
  improves code they're working in.
- Do NOT propose unrelated refactoring. Stay focused on the current goal.

## Key Principles

- **One question at a time** — never overwhelm with a batch.
- **Multiple choice preferred** — easier to answer than open-ended.
- **YAGNI ruthlessly** — remove unnecessary features from every design.
- **Explore alternatives** — always 2-3 approaches before settling.
- **Incremental validation** — present section, get approval, continue.
- **Be flexible** — go back and clarify when something doesn't make sense.

## Checklist
- [ ] Project context explored (files, commits, conventions)
- [ ] Scope assessed; decomposed if multi-subsystem
- [ ] Clarifying questions asked one at a time
- [ ] 2-3 approaches proposed with a recommendation
- [ ] Design presented in sections, each approved
- [ ] `contexts/{feature-name}/00-spec.md` written and committed
- [ ] Spec self-review passed (no placeholders / contradictions / ambiguity)
- [ ] User reviewed the spec file
- [ ] Handed off to planner, not implementer
