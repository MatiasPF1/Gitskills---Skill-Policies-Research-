# Safe Commit & Push

Non-destructive git workflow with mandatory approval gates for anything that
rewrites history, force-pushes, or touches remote branches.

## Hard Rules (never skip)

1. **Narrate every step** — before running any git command, state what you are
   about to do and why, in plain language.
2. **No destructive action without explicit approval.** Destructive means:
   `--force`, `--force-with-lease`, `reset --hard`, `clean -fd`, `rebase`,
   `commit --amend` (when pushed), `push --delete`, `branch -D`. State the
   exact command, explain the risk, and wait for "yes" / "go" / "approved".
3. **Never push to `main` or `master`** — always use a feature branch.
4. **Never commit secrets** — scan staged files for `.env`, `*.pem`, `*.key`,
   `credentials*`, `*secret*`, `token` patterns. Warn and exclude if found.
5. **Never skip pre-commit hooks** — no `--no-verify`.
6. **Stash is sacred** — if `git stash list` shows entries, mention them before
   any operation that could affect the stash (checkout, rebase, reset).
7. **Conflict = full stop** — if any operation produces a merge conflict, stop
   immediately, show the conflicted files, and ask the user how to proceed.
   Never auto-resolve.

## Pre-flight (always run first)

Run these **in parallel** at the start of every invocation:

```bash
git status --porcelain
git stash list
git branch --show-current
git remote -v
git log --oneline -5
git diff --stat
git diff --staged --stat
```

From the output, determine and report:

| Check                  | What to report                                                  |
| ---------------------- | --------------------------------------------------------------- |
| **Current branch**     | Name. If `main`/`master`, warn — must create or switch branch.  |
| **Dirty state**        | Unstaged changes, staged changes, untracked files — counts.     |
| **Stash**              | Number of stash entries (mention if > 0).                       |
| **Remotes**            | `origin` (fork) and `upstream` (if present).                    |
| **Tracking**           | Does the branch track a remote? Is it ahead/behind?             |
| **Recent commits**     | Last 5 one-liners for context.                                  |

Print a **Status Summary** block before proceeding:

```
--- Status Summary ---
Branch: fix/PROJ-12345
Tracking: origin/fix/PROJ-12345 (ahead 1, behind 0)
Uncommitted: 2 modified, 1 untracked
Staged: 0 files
Stash: empty
Remotes: origin → your-username/your-repo (fork), upstream → upstream-org/your-repo
-----------------------
```

## Detect Scenario

Based on pre-flight, auto-detect and confirm with the user:

| Signal                                          | Scenario                          |
| ----------------------------------------------- | --------------------------------- |
| On `main`/`master` + uncommitted changes        | **A — New branch needed**         |
| On `main`/`master` + no changes                 | **A — New branch needed** (or nothing to do) |
| On feature branch + uncommitted changes         | **B — Commit to existing branch** |
| On feature branch + no changes + ahead of remote | **C — Push only**                |
| On feature branch + behind upstream/main        | **D — Sync needed**              |
| User explicitly asks to amend                   | **E — Amend last commit**        |
| User explicitly asks to create PR               | **F — Hand off to create-pr**    |

State which scenario you detected: *"It looks like Scenario B — you have
uncommitted changes on `fix/PROJ-12345`. I'll stage, commit, and push.
Sound right?"* — wait for confirmation before proceeding.

## Scenario A — New branch for new work

Use when the user is on `main`/`master` or explicitly asks to start new work.

### A1. Sync main with upstream

```
Now: Fetching latest upstream/main.
```

```bash
git fetch upstream
```

Check if local main is behind upstream/main:

```bash
git rev-list --count HEAD..upstream/main
```

If behind, pull (fast-forward only — safe):

```bash
git checkout main
git merge --ff-only upstream/main
```

If `--ff-only` fails, **stop** — local main has diverged. Ask user before
proceeding. This should not normally happen.

### A2. Create branch

Ask the user for a branch name if not provided. Suggest based on context:

- Ticket key in conversation → `fix/PROJ-XXXX` or `feature/PROJ-XXXX` (adjust prefix to your tracker)
- User's prefix preference: `fix/`, `feature/`, `chore/`

```bash
git checkout -b <branch-name>
```

Confirm: *"Created branch `fix/PROJ-12345` from `main`. Ready for commits."*

Then proceed to **Scenario B** for committing.

## Scenario B — Commit changes on existing branch

The most common path. User has changes to commit on a feature branch.

### B1. Secrets scan

Before staging, check modified/untracked files for dangerous patterns:

```bash
git diff --name-only
git diff --staged --name-only
git ls-files --others --exclude-standard
```

Flag any file matching: `.env*`, `*.pem`, `*.key`, `*credential*`, `*secret*`,
`*token*`, `*.p12`, `*.pfx`, `id_rsa*`. If found:

> **Warning: `<filename>` looks like it may contain secrets. I will NOT stage
> this file. If you're sure it's safe, tell me explicitly to include it.**

### B2. Stage files

List files to be staged, then `git add -A` (or specific paths if user requested
partial staging). Exclude any files flagged in B1.

### B3. Review diff

Run `git diff --staged --stat`. For small diffs (< 100 lines), show the full
diff. For large diffs, show stat and offer file-by-file.

### B4. Compose commit message

Write a **single-line conventional commit** — no body, no multi-line:

```
<type>(<scope>): <short imperative summary>
```

Types: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `style`, `perf`.
Keep under 72 characters. Show and ask for approval before committing.

### B5. Commit

Only after the user approves the message:

```bash
git commit -m "fix(ui): improve loading and empty state accessibility"
```

If the commit fails (pre-commit hook rejection, etc.), show the error and help
fix it. **Never retry with `--no-verify`.**

### B6. Push

Check tracking with `git rev-parse --abbrev-ref --symbolic-full-name @{u}`.

- **Already tracking** → `git push`
- **First push** → `git push -u origin HEAD`
- **Push rejected** (remote has new commits) → offer options:
  1. Pull and merge (safe): `git pull --no-rebase`
  2. Pull and rebase (approval needed)
  3. Abort — do nothing
  Never force push here. Wait for the user to choose.

### B7. Confirm

Print the commit message, remote/branch pushed to, and PR status (URL if one
exists, or suggest creating one).

## Scenario C — Push only (no new commits needed)

Branch has unpushed commits but no uncommitted changes.

```
Now: You have <N> unpushed commit(s) on `<branch>`. Pushing to origin.
```

```bash
git push
```

If rejected, follow the same rejection handling as B6.

## Scenario D — Sync branch with upstream

Use when the feature branch is behind `upstream/main` and needs updating.

### D1. Fetch

```
Now: Fetching latest from upstream.
```

```bash
git fetch upstream
```

### D2. Check divergence

```bash
git rev-list --left-right --count HEAD...upstream/main
```

Report: *"Your branch is X commits ahead and Y commits behind upstream/main."*

### D3. Choose strategy (ask user)

> **Your branch is behind upstream/main by Y commits.**
> Options:
> 1. **Rebase** onto upstream/main — cleaner history, but rewrites your
>    commits. **Requires force-push if already pushed.** (approval needed)
> 2. **Merge** upstream/main into your branch — safe, no rewrite, creates
>    merge commit.
> 3. **Skip** — do nothing for now.
>
> Which option?

### D4a. Merge path (safe)

```bash
git merge upstream/main --no-edit
```

If conflicts → **full stop**. Show conflicted files:

```bash
git diff --name-only --diff-filter=U
```

> **Merge conflict in N file(s):**
> - `src/components/Foo.tsx`
> - `src/utils/bar.ts`
>
> I've stopped the merge. You can:
> 1. Resolve conflicts manually, then tell me to continue
> 2. Abort the merge: `git merge --abort` (safe, returns to pre-merge state)

Never auto-resolve. Wait for the user.

After conflicts are resolved: `git merge --continue`

### D4b. Rebase path (destructive — approval required)

**Before proceeding, require explicit approval:**

> **Approval required:** I will run `git rebase upstream/main`. This rewrites
> your local commits. If you've already pushed this branch, you will need to
> force-push afterward. Approve?

Only after "yes" / "approved":

```bash
git rebase upstream/main
```

If conflicts → **full stop** with the same conflict handling as D4a, but using
`git rebase --abort` and `git rebase --continue`.

After successful rebase, if the branch was already pushed:

> **Approval required:** Rebase succeeded. The branch was previously pushed, so
> updating the remote requires `git push --force-with-lease`. This overwrites
> the remote branch. Approve?

Only after approval:

```bash
git push --force-with-lease
```

`--force-with-lease` (not `--force`) protects against overwriting someone else's
commits on the remote branch.

## Scenario E — Amend last commit

Only when the user explicitly asks to amend.

### E1. Safety checks

```bash
git log -1 --format='%H %s'
git rev-parse --abbrev-ref --symbolic-full-name @{u} 2>/dev/null
git rev-list --count @{u}..HEAD 2>/dev/null
```

Determine:

- **Not pushed yet** (ahead of remote, or no upstream) → safe to amend.
- **Already pushed** → amending requires force-push. Warn prominently.

### E2. If not pushed (safe)

```
Now: Amending the last commit (not yet pushed — safe).
```

Stage new changes if any, then:

```bash
git commit --amend -m "$(cat <<'EOF'
<updated message>
EOF
)"
```

Or `git commit --amend --no-edit` if only adding files without changing message.

### E3. If already pushed (destructive — double approval)

> **Warning:** The last commit has already been pushed to
> `origin/<branch>`. Amending it will rewrite history and require a
> force-push.
>
> **Risks:**
> - Anyone who pulled this branch will have conflicts
> - CI runs on the old commit become orphaned
>
> **Are you sure you want to amend and force-push?** (say "yes, amend and
> force-push" to confirm)

Only after **explicit, specific** approval:

1. `git commit --amend ...`
2. `git push --force-with-lease`

## Scenario F — Create PR

When the user wants to create a pull request after pushing:

> Your branch is pushed and ready. To create a PR, I recommend using the
> **create-pr** skill which handles PR title, description, draft preview,
> and approval before opening. Shall I proceed with that?

If yes, follow the `create-pr` skill workflow. Typical defaults:

- Base branch: `main` on `upstream` (use your fork’s default base — e.g. `upstream-org/your-repo` on GitHub)
- PR via: `gh pr create`
- Draft preview before opening

## Edge Cases

- **Detached HEAD** → warn; offer `git checkout -b <name>` or switch to existing
  branch. Do not commit in detached state.
- **Uncommitted changes + need to switch** → offer: stash, commit first, or
  discard (discard requires approval).
- **No `origin` remote** → tell user to add fork remote before pushing.
- **Nothing to commit or push** → report clean state, no action needed.

## Transparency Format

Use this structure for every step so the user always knows where they are:

```
--- Step N: <Step Name> ---
Now:  <what I am doing right now>
Next: <what happens after this>
---
```

For approval gates:

```
--- Approval Required ---
Action: <exact command or operation>
Risk:   <what could go wrong>
Why:    <why this needs approval>
---
Approve? (yes / no / abort)
```
